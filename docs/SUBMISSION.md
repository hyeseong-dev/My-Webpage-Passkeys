# 패스키 소개 페이지 제출 기록

결과물 URL: https://my-webpage-passkeys.vercel.app

소스 URL: https://github.com/hyeseong-dev/My-Webpage-Passkeys

기준일: 2026-09-11. 공개 소개는 작성자가 공개 범위를 선별한 실제 자기소개다. 패스키 계정과 비공개 자료는 인증 기능 검증을 위해 만든 합성 예시이며, 인증기에는 실습용 이름을 사용한다. 연락처와 `/career`의 상세 지원 정보는 이 제출본에 포함하지 않았다.

## 현재 완료 범위와 남은 확인

홈페이지와 WebAuthn 패스키 기능을 구현했고, 별도 배포 및 Neon의 6개 테이블 구성을 완료했다. 로컬 서버 테스트 20개와 실제 배포 API를 대상으로 한 HTTP 검증 36개가 통과했다. [인증 구현 설명서](AUTHENTICATION.md)와 [실제 요청·응답 증거](evidence/deployed-api.json)를 함께 제출한다.

실서버 검증은 실제 서명을 만드는 소프트웨어 인증기를 사용했다. 실기기의 패스키 승인, 저장 제공자, 두 실제 계정과 계정당 패스키 두 개의 현재 보유 상태는 아직 사용자 확인이 필요하다. 자동 검증에서 만든 임시 계정은 마지막 패스키 삭제 API로 모두 정리했으므로, 기록만 남아 있고 해당 계정에 계속 로그인할 수는 없다.

**T08-C11은 충족한다.** 1번 과제의 `/` 공개 소개 내용과 세 가지 이야기, 학습 기록 링크를 보존하고 그 아래에 패스키 영역을 이어 붙였다. 기존 `/career`의 연락처·상세 경력·지원 정보는 1번 과제의 공개 소개 범위가 아니므로 가져오지 않았다.

**T08-C12는 적용 범위를 명시한다.** 자기소개 과제의 공개 본문은 작성자가 공개하기로 선별한 실제 정보다. 반면 패스키 계정과 비공개 기록은 전부 합성 데이터이며 화면과 문서에 이를 표시했다. 따라서 C12를 공개 자기소개까지 모두 허구로 만들라는 뜻이 아니라, 인증 실습에 불필요한 실제 개인정보와 비공개 자료를 넣지 말라는 취지로 해석했다.

쿠키나 인증 헤더가 없는 새 HTTP 요청으로 결과물과 공개 소스 모두 리다이렉트 없이 `200` 응답을 확인했다. 운영 화면 제목은 `이혜성의 자기소개 | 패스키 교육용 데모`, 공개 소스 제목은 `hyeseong-dev/My-Webpage-Passkeys · GitHub`였다. 이 요청은 실제 시크릿 브라우저 창은 아니므로, 명세 문구 그대로의 시크릿 창 확인은 사용자 확인으로 구분한다.

운영 브라우저에서는 초기 기록함 잠김, 비공개 노트의 DOM 미포함, 비밀번호 입력란 0개, 콘솔 오류 0개를 확인했다. 너비 1280px 화면에서 가로 넘침도 없었다. 실제 패스키 승인 후의 화면 검증은 여전히 대기다.

배포 HTML이 참조한 자바스크립트 번들에서도 비공개 기록 템플릿, DB 연결 문자열, 기존 실명이 검출되지 않았다. `/.env.local` 및 서버 소스 직접 URL은 `404`, 비로그인 비공개 API는 `401`과 `Cache-Control: no-store, private`을 반환했다. 운영 의존성을 보안 패치한 뒤 `pnpm audit --prod --audit-level=low`에서 알려진 취약점 0건을 확인했다. 이는 개발 의존성 전체나 알려지지 않은 결함이 없다는 보장은 아니다.

## 짧은 확인 방법

### ① 어디로 가나요

위 결과물 URL을 새 시크릿 창에서 연다. 첫 화면의 공개 소개는 패스키를 만들지 않아도 읽을 수 있다. 상단 ‘패스키로 여는 비공개 영역’을 누르면 기록함으로 이동한다.

### ② 세 단계 안에 무엇을 하나요

1. 잠긴 기록함에서 실습용 패스키 이름을 입력하고 ‘새 데모 계정 만들기’를 누른다. 브라우저 인증 창의 승인은 사용자가 직접 진행한다.
2. 열린 기록함에서 자료 3개와 패스키의 이름·등록일을 확인한다.
3. ‘로그아웃’을 누르고 기록이 숨겨지는지 확인한 뒤, ‘패스키로 로그인’으로 다시 연다.

### ③ 무엇이 보이면 통과인가요

등록하지 않은 상태에서도 공개 소개가 보인다. 인증 전에는 비공개 자료 본문이 없고, 인증 후에는 같은 계정의 가상 기록 3개와 등록한 패스키 목록이 보인다. 로그아웃하면 기록함이 다시 잠긴다.

### ④ 안 될 때는 무엇이 보이나요

등록이나 로그인을 취소하면 취소·시간 초과 안내가 나타나고 자료가 열리지 않는다. 세션이 없거나 만료되었을 때 비공개 API는 `401`, 다른 계정의 자료에는 `403`을 반환한다. 서버 연결이 안 되면 연결 안내와 재확인 버튼을 표시하고, 다른 배포 주소라면 정식 홈페이지로 이동하도록 안내한다.

## 실기기로 추가할 기록

아래는 완료 사실이 아니라 사용자 실습 후 작성할 항목이다. 계정 이름과 패스키 이름은 실습용 별칭을 쓰고 쿠키·세션 토큰은 공개하지 않는다.

| 확인할 것 | 현재 상태 | 완료 후 남길 근거 |
| --- | --- | --- |
| 첫 실제 패스키 등록과 인증 창 취소 | 사용자 확인 대기 | 성공한 등록 화면, 취소 안내, 등록 전후 credential 수 |
| 선택한 실제 저장 위치 | 미확인 | 사용자가 선택한 Google 비밀번호 관리자·기기 자체·보안 키 등 실제 제공자명 |
| A 계정에 패스키 2개 | 소프트웨어 API 검증만 완료; 임시 키는 삭제됨 | 등록된 두 키의 이름·등록일 목록 |
| B 계정 생성과 자료 분리 | 소프트웨어 API 검증만 완료; 임시 계정은 삭제됨 | 다른 세션에서 만든 B의 표시 이름과 서로 다른 가상 자료 |
| A의 키 하나 삭제 후 남은 키 로그인 | 소프트웨어 API 검증만 완료 | 실기기 삭제 결과와 남은 키 로그인 결과 |
| 삭제한 키 로그인 실패 | 소프트웨어 API 검증만 완료 | 삭제한 키를 선택한 로그인 실패. 기기 저장소의 항목이 자동으로 지워지지 않을 수 있음 |

모든 패스키를 잃으면 기존 계정을 복구할 수 없다. 마지막 패스키를 서버에서 삭제하면 즉시 로그아웃되며 계정과 합성 자료도 삭제된다. 이 작업 후 새 계정을 만들더라도 이전 기록은 이어지지 않는다.

## 항목별 판정

원문에는 C01~C03과 C10~C53이 있어 **총 47개 항목**이다. C04~C09는 제공된 명세에 없으므로 새 요구사항을 만들어 추가하지 않았다.

판정에서 ‘확인’은 근거가 적힌 범위의 구현·기록 확인을 뜻한다. ‘API 확인’은 소프트웨어 인증기가 실제 배포 서버를 상대로 확인했다는 뜻이며 실기기 승인까지 뜻하지 않는다. ‘부분 확인’은 기능 또는 자동 기록은 있지만 요구하는 현재 실기기 상태·화면 증거가 남아 있다는 뜻이다. 전체 항목을 일괄 통과로 표시하지 않는다.

## 증거를 읽을 때의 구분

- [deployed-api.json](evidence/deployed-api.json)은 실제 배포 API·Neon의 성공/거절 기록이다. 브라우저 자동화나 실기기 생체 인증 증거는 아니다.
- [handler.test.ts](../server/passkeys/handler.test.ts)는 로컬 독립 DB에서 20개 서버 사례를 검증한다. 실제 운영 부하 테스트로 해석하지 않는다.
- 자동 검증의 임시 계정·공개키·항목 ID와 본문은 교육용으로 생성한 값이다. 검증 종료 시 계정과 자료를 삭제했다. 실제 이용자의 자료·세션·개인키는 증거에 넣지 않는다.
- T08-C12의 적용 범위와 실제 기기 검증 범위는 공개 저장소를 제출할 때도 남긴다. 구현된 기능, 자동으로 확인한 동작, 사람이 확인해야 할 항목을 구분한다.
